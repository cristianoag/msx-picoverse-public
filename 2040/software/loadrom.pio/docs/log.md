## PicoVerse 2040 Loadrom v2.65

- Version bumped to v2.65 (top-level and tool Makefiles).
- Moved all five RP2040 firmwares (`pico/loadrom`, `pico/keyboard`, `pico/midi`, `pico/midipac`, `pico/joystick`) from Pico SDK 2.2.0 to Pico SDK 2.3.1 (including its bundled TinyUSB), from the Arm GNU Toolchain 13.3.Rel1 to 15.2.Rel1 (GCC 15.2.1) and from picotool 2.2.0-a4 / 2.1.1 to 2.3.1. Each `CMakeLists.txt` now sets `sdkVersion 2.3.1`, `toolchainVersion 15_2_Rel1` and `picotoolVersion 2.3.1`; the keyboard, midi, midipac and joystick files carry the extension's version block twice, and both copies were updated so the later one (which used to pin picotool 2.1.1) no longer overrides the first. The SDK, toolchain, picotool and pioasm are expected under `~/.pico-sdk/sdk/2.3.1`, `~/.pico-sdk/toolchain/15_2_Rel1`, `~/.pico-sdk/picotool/2.3.1` and `~/.pico-sdk/tools/2.3.1`. The old `pico/*/build` directories must be removed once so CMake reconfigures (`make clean` does this).
- Clean `make all` builds all five firmwares and the tool without source changes. `dist/*.bin` sizes (bytes, old to new): loadrom 44500 to 42656, keyboard 28796 to 26984, midi 27460 to 25512, midipac 61172 to 59864, joystick 32036 to 30876. The embedded headers and `tool/dist/loadrom.exe` were regenerated.
- `tool/Makefile` now embeds `pico/joystick/dist/joystick.bin` into `tool/src/joystick_fw.h` like the other firmwares (new rule, build dependency and `clean` entry). Before, that header was a stale hand-made copy that the build never refreshed, so `-j` would have kept shipping the previous joystick firmware. It is now generated by `xxd` with the same symbol name, and a `-j` UF2 was generated with the new 30876-byte image.
- Sanity check: the rebuilt tool generates UF2 files for the keyboard (`-k`) and joystick (`-j`) firmwares. None of the firmwares has been tested on hardware yet; the MSX bus, USB host and MIDI paths need a check on a real MSX with the new SDK and compiler before release.

## PicoVerse 2040 Loadrom v2.64

- Version bumped to v2.64 (top-level and tool Makefiles).
- Added the `-s3` / `--sunrise3` and `-m3` / `--mapper3` tool options for testing Nextor 3, modelled on the 2350 Explorer/LoadROM `-s3` implementation. They build `Nextor Sunrise 3.0.0 Beta 2` and `Nextor Sunrise 3.0.0 Beta 2+Mapper` system images with Konamiman's Nextor 3.0.0 beta 2 Sunrise IDE MasterOnly kernel (128 KB, SunriseIDE-Nextor-driver `v0.1.8-blueMSX-v0.1.5-Nextor-3.0-beta.2` release, same ROM as the 2350 projects). They reuse the existing Sunrise (10) and Sunrise+Mapper (11, 192KB mapper) types, so the RP2040 firmware is unchanged; the beta 2 driver sends the same ATA commands as 2.1.4. Booting beta 2 on hardware is not yet validated.
- `-s`, `-m`, `-s3` and `-m3` are now mutually exclusive, and `-k`, `-i`, `-p`, `-j` reject all four. The Nextor modes still reject an external ROM file. The tool refuses to build a Nextor image whose embedded kernel is not 128 KB. The `-h` help text lists the new options and labels `-s`/`-m` as Nextor 2.1.4.
- Renamed `nextor/kernel/` to `resources/`, which now holds both `Nextor-2.1.4.SunriseIDE.MasterOnly.ROM` and `Nextor-3.0.0-beta2.SunriseIDE.MasterOnly.ROM`. `tool/Makefile` embeds them from there as `tool/src/nextor_sunrise.h` (symbol now `___resources_Nextor_2_1_4_...`) and the new `tool/src/nextor3.h`, and cleans both headers. Removed the stale commented-out non-MasterOnly kernel path.
- Fixed `create_uf2_file()` copying a fixed 50 bytes from the ROM name, which read past the short Nextor name literals and filled the rest of the config-record name field with unrelated strings. The name is now copied up to its terminator into the zero-filled record. A regular ROM UF2 is byte-identical to v2.63's.
- Checked `-s`, `-m`, `-s3` and `-m3` UF2s: firmware, record type (10/11), size, offset and the embedded kernel bytes match the expected 2.1.4 or 3.0.0 beta 2 ROM. Rebuilt `tool/dist/loadrom.exe`.
- Docs: 2040 LoadROM tool manual (option matrix, options, Nextor 3 workflow, limitations), the 2040 Sunrise Nextor implementation notes (embedded kernels and record names) and the public README.
## PicoVerse 2040 Loadrom v2.63

- Version bumped to v2.63 (top-level and tool Makefiles).
- `../tools/gen_romdb.py` now downloads the latest database by default from Vampier's ROM DB (`https://romdb.vampier.net/Archive/xml-msxromsdb.zip`) and reads `softwaredb.xml` from the zip in memory, so a local openMSX install is no longer needed. A local `softwaredb.xml` or `.zip` can still be passed as an argument for offline use. The generated header now records the source and the database timestamp. The script also accepts the `ASCII16-X` and lowercase `konami` mapper names used by this database.
- Regenerated `tool/src/romdb.h` from the 2026-10-03 database: 3115 → 3218 entries (103 added, none removed or changed), including 31 ASCII16-X ROMs (mapper 12) that the old DB never matched. Rebuilt `tool/dist/loadrom.exe`.

## PicoVerse 2040 Loadrom v2.62

- Version bumped to v2.62 (top-level and tool Makefiles).
- Fixed lost bank-switch writes in every banked mapper loop (`banked8_loop` for Konami/Konami-SCC/ASCII8, plus ASCII16, ASCII16-X, Neo-8 and Neo-16). Those loops blocked on `pio_sm_get_blocking()` for the next cartridge read and only drained the memory write captor FIFO before and after it, so game code executing from MSX RAM that issued a burst of segment switches without any intervening cartridge read overflowed the 8-entry RX FIFO. The write state machine then stalled on `push block` and the extra switches were silently dropped, leaving the mapper register on a stale segment (and, with an ASCII16-X/Neo cache miss, forcing the bank refill to run while `/WAIT` was already asserted). Added `pio_get_read_draining_writes()`, which drains the memory write FIFO while waiting for the next read, and switched all banked loops to it. Same fix as PicoVerse 2350 Loadrom v2.70, reported with "Go Figure v1.2" (ASCII16-X), which alternates the page-1 segment twice per call from a page-3 RAM routine and hung on the palette cross-fade.
- Kept the new idle loop at the same read-response latency as the previous blocking wait by sampling `FSTAT` once per iteration and testing the read and write RX-empty flags from that single sample. Polling the two FIFOs with separate `pio_sm_is_rx_fifo_empty()` calls doubled the PIO register accesses in the loop, which on the Cortex-M0+ stretched `/WAIT` on every cartridge read enough to slow VDP transfer loops and trigger "VDP too slow" reports in timing-sensitive games.

## PicoVerse 2040 Loadrom v2.59

- Bumped the loadrom.pio version to v2.59.
- Changed the PIO LoadROM memory-read `/WAIT` driver to open-drain behaviour: the cartridge now pulls `/WAIT` low only while stretching its own slot read cycles and releases the shared line as hi-Z afterward, avoiding contention with another `/WAIT`-using cartridge in the other MSX slot.
- Changed the MIDI and joystick I/O read `/WAIT` responders to the same open-drain behaviour so those auxiliary firmware targets no longer drive the shared `/WAIT` line high when idle or after an I/O read response.

## PicoVerse 2040 Loadrom v2.58

- Bumped the loadrom.pio version to v2.58.
- Set all loadrom.pio firmware target system clocks to 230 MHz to improve stability with pico boards with bad quality flash memory.
